# lunaRun — Decision Log

Short architecture decision records. Add new ones at the bottom: `D-0NN`, date, status
(`accepted` / `superseded by D-0xx`), context, decision, consequences. Never delete a record. Supersede it.

---

### D-001 — Desktop framework: Tauri 2 (2026-10-29, accepted)
**Context:** We need one codebase for Windows/macOS/Linux, with installers built by GitHub Actions. The app sits in the tray all day.
**Options:** Electron (TypeScript only, ~100 MB+ installer, ~150–300 MB RAM) · Tauri 2 (Rust + TypeScript, ~10 MB, low RAM) · native per OS (rejected: several codebases).
**Decision:** Tauri 2. Rust is well suited to process supervision, archives and OS APIs (Job Objects, ports). The official `tauri-action` builds and releases all OSes, and there is a built-in signed updater.
**Consequences:** Two languages (Rust backend, TS frontend), but one codebase and one pipeline. Webview differences (WebView2 / WKWebView / WebKitGTK) need testing on each OS.

### D-002 — UI-free core crate (2026-10-29, accepted)
**Decision:** All logic lives in `crates/luna-core`, and `src-tauri` is a thin adapter.
**Consequences:** Unit-testable without a GUI. The `luna` CLI (Phase 2) reuses the core.

### D-003 — Runtimes are downloaded, not bundled (2026-10-29, accepted)
**Decision:** The installer contains only lunaRun. Runtimes are fetched on demand from upstream sources listed in the registry.
**Consequences:** Small installer. Users can pick any version. We avoid most redistribution obligations (GPL MySQL/MariaDB). The first run needs internet.

### D-004 — Web server for MVP: Caddy (2026-10-29, accepted)
**Context:** Nginx has official binaries only for Windows. Apache on Windows comes from third parties.
**Decision:** Caddy 2. It has official binaries for every OS/arch, simple config, a reload API, `php_fastcgi` built in, and a local CA for HTTPS later.
**Consequences:** Nginx/Apache become optional per-site engines in Phase 3.

### D-005 — PHP binaries on macOS/Linux: static-php-cli builds (2026-10-29, accepted)
**Context:** PHP publishes official binaries only for Windows.
**Decision:** Use static-php-cli builds (upstream prebuilt first, our own CI builds if needed; PRD Q3).
**Consequences:** One self-contained binary per version. Fixed extension set per build. No shared extensions (affects Xdebug, Q5). PHP < 8.1 is not offered on macOS/Linux in v1.

### D-006 — State in JSON files, filesystem is the source of truth for installs (2026-10-29, accepted)
**Decision:** Small JSON files with atomic writes and schema versions. Install receipts sit inside each runtime directory. No SQLite.
**Consequences:** Human-readable, easy to debug and back up. Revisit if data grows (e.g. request logs).

### D-007 — License: Apache-2.0 (2026-10-29, accepted)
**Options:** MIT (simplest) · Apache-2.0 (permissive + explicit patent grant + no trademark grant) · GPL-3.0 (forks must stay open, which discourages companies from contributing).
**Decision:** Apache-2.0. It is permissive enough to drive adoption, the patent grant protects contributors and users, and §6 grants no rights to the "lunaRun" name or logo, so forks can't pass themselves off as the project.
**Consequences:** Contributions are accepted under the same license (inbound = outbound, stated in CONTRIBUTING.md). Add a `NOTICE` file if third-party Apache code is ever included.

### D-008 — No telemetry (2026-10-29, accepted)
**Decision:** No analytics or crash reporting that phones home. Diagnostics are copied manually by the user.

### D-009 — Registry decoupled from app releases (2026-10-29, accepted)
**Decision:** The available-versions list is a separately hosted, generated `registry.json` (with a bundled fallback).
**Consequences:** New PHP/MySQL/Node releases appear without an app release. It must be hosted publicly even while the app repo is private (RUNTIMES §5).

### D-010 — Never write into user projects without consent (2026-10-29, accepted)
**Decision:** Detection is read-only. Any write (`.env`, `.lunarun.json`) is an explicit user action with a preview and a backup.

### D-011 — Frontend router: React Router, hash mode (2026-10-29, accepted)
**Context:** The app has about six sidebar pages and no URL bar, SEO or server rendering. Candidates: React Router 8, TanStack Router 1.x, wouter.
**Decision:** `react-router` (declarative mode) with a **hash** router (`createHashRouter`). The hash keeps the current page across a dev reload and works under Tauri's custom protocol without server-side fallback rules.
**Why not TanStack Router:** its main benefit (type-safe routes via code generation) adds a build step and concepts we don't need for this few routes. React Router is the most widely known, which helps contributors and AI agents.
**Consequences:** Route paths are plain strings, kept in one `src/app/routes.ts` module to avoid typos. Revisit if routing grows (nested data loading, many params).

### D-012 — Rust → TypeScript types: ts-rs (2026-10-29, accepted)
**Context:** IPC types must not be hand-duplicated (CLAUDE.md rule 11). `ts-rs` 12.0.1 is stable. `specta` / `tauri-specta` are still on 2.0 release candidates (`2.0.0-rc.x`), and their 1.x stable lines target Tauri v1.
**Decision:** `ts-rs`. IPC structs/enums in `luna-core` derive `Serialize + Deserialize + TS` with `#[serde(rename_all = "camelCase")]` and `#[ts(export)]`. Generated files land in `src/bindings/` and are **committed**. `.cargo/config.toml` sets `TS_RS_EXPORT_DIR`. Files regenerate on `cargo test`. CI fails if `git diff --exit-code src/bindings` shows a difference (added with the CI task).
**Conventions** (verified by a spike):
- `u64`/`i64` become `bigint` in TS, but Tauri's JSON gives a plain `number`. Annotate such fields with `#[ts(type = "number")]` (byte counts, timestamps).
- Tagged enums use `#[serde(tag = "kind", rename_all = "camelCase")]` so TS gets a discriminated union.
- `src/lib/ipc.ts` holds thin typed `invoke` wrappers, one per command, importing only from `src/bindings/`.
**Consequences:** Command names and argument shapes are still written twice (Rust handler, TS wrapper), but payload types cannot drift. If that becomes painful, revisit `tauri-specta` once it reaches a stable 2.0 (supersede this record).

### D-013 — CI cost control while the repo is private (2026-10-30, superseded by D-015)
**Context:** Every working session ends with a push to `main`. On a private repo GitHub Free gives a monthly minute quota, and Windows runners count x2 and macOS x10. Running `cargo test` on both after every push would use the quota in a few weeks.
**Decision:** Per push and pull request, CI runs only on Ubuntu (lint, test, debug build) and skips docs-only changes. The Windows and macOS test matrix runs on `workflow_dispatch` (manual) and is exercised again by the release workflow on tags. Windows is also tested locally by the developer.
**Consequences:** A macOS-only break can go unnoticed until a manual run or a release tag. Run the matrix manually (`gh workflow run CI`) after touching OS-specific code. When the repo goes public (free minutes), change `test-os` to run on push to `main`.

### D-014 — HTTP client: reqwest with rustls and the OS trust store (2026-10-30, accepted)
**Context:** Runtimes are downloaded from several upstream hosts (D-003), on Windows, macOS and Linux, often behind corporate proxies and TLS-inspecting firewalls.
**Decision:** `reqwest` 0.13 with `default-features = false` and the `rustls`, `http2`, `stream` and `system-proxy` features. `rustls` brings the OS certificate store (`rustls-platform-verifier`), so a company root CA that Windows trusts also works here, and the aws-lc-rs crypto provider. System proxy settings are honoured. Redirects are checked by our own policy so an HTTPS URL can never lead to plain HTTP. Plain HTTP on loopback exists only behind `DownloadOptions::loopback_test()`, which the app never uses.
**Consequences:** No OpenSSL dependency and no system C library to install. aws-lc-rs built without extra tools on Windows (verified locally; Linux in CI). The cold build is about 1.7 minutes longer. If that becomes a problem, switch to `rustls-no-provider` with the `ring` provider.

### D-015 — Public repository: free CI, automatic publishing, permanent download names (2026-10-30, accepted)
**Context:** The owner made the repository public. That removes the private-repo minute budget behind D-013, and the README needs download links that keep working for every new version.
**Decision:** (1) The Windows and macOS Rust tests run on every push. (2) A tag publishes its release automatically, but only after all three platform builds succeed: the build creates a hidden draft and a final `publish` job (`scripts/finalize-release.mjs`) renames the installers to fixed names such as `lunaRun-windows-x64-setup.exe` and publishes. (3) The README links to `releases/latest/download/<fixed name>`. (4) Manual builds (Actions tab) default to all platforms and keep their installers as artifacts.
**Why rename instead of using `releaseAssetNamePattern`:** the pattern's `[arch]` and `[ext]` values differ per bundle type (`amd64`, `x86_64`, `.app.tar.gz`), which cannot be predicted without running a release. Renaming by a tested rule is deterministic and was verified against the real `v0.0.1` asset list.
**Consequences:** Files lose the version in their name (the version is the release tag and title). A bad tag can still publish a broken-but-complete build, so `check-versions` runs first and a release can be unpublished or deleted by the owner. The updater (Phase 2) must switch to `releaseAssetNamePattern` so `latest.json` matches.

### D-016 — Archive extraction: own safe extractor on zip, tar, flate2 and lzma-rust2 (2026-10-30, accepted)
**Context:** Runtimes arrive as `.zip` (Windows PHP, Node, MariaDB), `.tar.gz` (Caddy, macOS) and `.tar.xz` (Node on Linux, MySQL). Archives from the internet are hostile input: the classic attacks are zip-slip (`../` names), links that point outside, writing through a link created earlier in the same archive, special files, and decompression bombs. The libraries' own "unpack" helpers have had path-traversal bugs, so we do not rely on them.
**Decision:** `luna-core::extract` reads entries with the `zip` crate (default features off, deflate only), the `tar` crate (reading only, never its `unpack`), `flate2` (pure-Rust backend) and the pure-Rust `lzma-rust2` for `.xz`. Our own code validates every path and writes every file. Rules: no absolute, drive-letter, UNC or `..` paths (both `/` and `\` separate); the destination must be empty so we can track every symlink we create and refuse to write through one (also compared case-insensitively); symlinks only on Unix and only with a relative target that stays inside; hard links only to a regular file extracted earlier; `create_new` for files (no overwrite, never follows a link); special files refused; limits on total size, per-file size and entry count counted from real bytes; XZ decoder memory capped; setuid/setgid/sticky dropped.
**Why lzma-rust2 and not liblzma/xz2:** pure Rust means no C compiler or system library on any CI runner or user build, the crate is actively maintained (0.24 in October 2026), and it includes an encoder, which lets the tests build `.tar.xz` files in code. Compatibility was checked against a file made by the official liblzma and against Node's real 32 MB `.tar.xz` (4,797 files, 201,760,169 bytes, identical to Python's count). Trade-off: a pure-Rust decoder is slower (31 s for that file in a debug build, not yet measured in release).
**Consequences:** Windows refuses symlinks inside archives, which is fine because Windows runtimes ship as zips without them. Extraction is not atomic, so the caller extracts into a fresh `.staging-*` folder and deletes it with `safe_remove` on failure. If XZ speed hurts in the UI, measure a release build first, then consider `liblzma` or the multi-threaded reader in `lzma-rust2`.

### D-017 — Registry generator: where checksums come from, and MySQL by pinned signature (2026-11-02, accepted)
**Context:** The registry pins a SHA-256 for every download (NFR-05), but upstreams publish different things: Node, PHP for Windows, MariaDB and Composer publish SHA-256; Caddy publishes only SHA-512; MySQL publishes MD5 on web pages that answer 403 to scripts, plus detached GPG signatures. Upstream sizes are sometimes rounded.
**Decision:** (1) A SHA-256 published by the upstream is copied as it is. (2) Where upstream publishes only another strong hash (Caddy, SHA-512), the file is downloaded once, must match that hash (and GitHub's digest when shown), and the SHA-256 computed from those bytes is pinned. (3) **MySQL** has no machine-readable release list, so versions and end-of-life dates come from `endoflife.date`, download addresses follow the documented CDN naming (HEAD says whether a build exists), and each new download is streamed once through `gpg --verify` against its detached `.asc`. The signer must be exactly the **pinned fingerprint of the MySQL Release Engineering key** (`BCA43417C3B485DD128EC6D4B7B3B788A8D3785C`, the same on repo.mysql.com and the keyservers); the key file itself is fetched from keyserver.ubuntu.com, because the copy on repo.mysql.com has a stale expiry date and gpg then reports `EXPKEYSIG`, which the generator treats as a failure. The computed SHA-256 is pinned. (4) A version already in the previous registry is reused, never downloaded again (release assets do not change). (5) Exact sizes come from HEAD requests with `Accept-Encoding: identity`.
**Consequences:** `gpg` is needed to refresh MySQL (generator and CI only, never the app); a missing gpg fails MySQL loudly and keeps its previous entry. The first MySQL run downloads about 4.6 GB (later runs only new releases). Linux arm64 MySQL is left out for now because it would add about 2.7 GB to that first run. MySQL's CDN keeps only the current release of each line, so a stale registry can point at a file that has moved to the archive; the daily refresh limits that. If MySQL ever publishes SHA-256 or a readable index, this simplifies.
**Follow-up (static PHP, same day):** static-php-cli's builds for macOS and Linux have no checksum and no signature at all, so their SHA-256 is computed from the generator's own download and carries **no upstream authentication**: it detects later tampering and transport damage, not a bad build at the source. This is the weakest trust level in the registry. Each such artifact records `builtAt` and is downloaded again when that date changes, so a rebuilt file is re-pinned instead of failing for users. The UI should mark these as community builds (M1.3), and a self-built, signed alternative stays open (PRD Q3).

### D-018 — Registry hosting: the main repository, refreshed by a daily pull request (2026-11-02, accepted)
**Context:** The app must fetch the registry without authentication, and the registry must change without an app release (D-009). Until the repository went public (D-015) that was impossible from a private repo. RUNTIMES §5 listed a separate public `lunarun-registry` repository as the preferred option.
**Decision:** Keep `registry/registry.json` in the main repository and serve it from `raw.githubusercontent.com/userAshwani/lunaRun/main/registry/registry.json`. A daily workflow (`registry.yml`) regenerates it, runs the app's parser tests on the result and opens a pull request that the owner merges; a failing upstream keeps its previous entry and turns the run red. The app also embeds the very same file at build time as its offline fallback (`include_str!` of the file, not a copy).
**Why not a separate repository now:** it would add a second place to maintain, a cross-repository token for the pull request, and a fallback copy that can drift. The URL is one constant, so moving later costs one line plus redirecting old clients.
**Consequences:** The registry only changes when a human merges the refresh (deliberate: a person sees every new download address and hash before users do). Raw content is cached for about five minutes. A pull request opened with the workflow token does not start CI, hence the parser tests inside the workflow. The setting *Allow GitHub Actions to create and approve pull requests* has to be on, otherwise the workflow pushes the branch and warns. Phase 2 adds signature verification of the registry (NFR-05); until then trust rests on the repository's own access control and review.

### D-019 — Install flow: staging folders, merged parts, a swappable fetcher, `fs4` for free disk space (2026-11-03, accepted)
**Context:** An install must never leave something a later listing could mistake for a working runtime, even after a crash, a cancel or a hostile archive. PHP on macOS and Linux is two flat archives (`php`, `php-fpm`) that must end up in one folder, while the extractor requires an empty destination (D-016). The install also needs the free disk space, which std cannot report.
**Decision:** (1) All work happens in hidden folders under `runtimes/<runtime>/`: `.extract-<job>-<n>` (one per archive) and `.staging-<job>`. The top-level entries of every extracted part are moved into the staging folder with **no overwrite** (two parts that contain the same name are a registry error), `format: file` artifacts are copied under the file name in their address, then `post_install`, then `verify` (which starts the new program) run **inside the staging folder**, the receipt is written last, and one `rename` makes it `runtimes/<runtime>/<version>/`. A folder with a plain version name is therefore always complete and verified. (2) Any failure, cancel or panic removes the work folders (a drop guard) and the downloaded archives, except after a cancel or a network error, when downloads are kept so the next try resumes. `cleanup_incomplete` removes `.staging-*` and `.extract-*` at startup and keeps partial downloads. (3) Checks before any download, in this order: adapter exists, not already installed, a download exists for this computer, prerequisites (`requires[]`, a pluggable function; the real Windows checks are M1.3 task 4), free disk (3 x the download size, `INSUFFICIENT_DISK`; if the free space cannot be read the install is not blocked). (4) The download step is a `Fetcher` function value, defaulting to the real resumable `Downloader`, so install logic is tested with a fake network (the registry only accepts `https://`, and the download engine has its own loopback tests). (5) Free disk space comes from the pure-Rust `fs4` crate (1.1.0, MIT or Apache-2.0): reading it needs `statvfs` on Unix and `GetDiskFreeSpaceEx` on Windows, whose struct layouts differ per OS and would need hand-written `unsafe` FFI.
**Consequences:** `verify` runs the new binary from the staging path, so a runtime that embeds absolute paths at first run must not do that during `--version` (none does). The final rename refuses an existing target but between that check and the rename there is a tiny race with a second installer; jobs are deduplicated by `<runtime>@<version>`, so only a second process could trigger it. The memory of a cancelled install is the kept download, never the staging folder. Free-space is measured on the disk that holds `LUNA_HOME`, which is also where downloads and staging live.

### D-020 — PHP configuration: edit the real `php.ini-development` in place, ship Mozilla's CA bundle, no template engine (2026-11-03, accepted)
**Context:** Every installed PHP needs a `php.ini` with Laravel-friendly settings (FR-RT-09) and, on Windows, a CA bundle: Windows PHP has no certificate store, so Composer and every HTTPS call from PHP fail with SSL errors. SERVICES §4 named `minijinja` for templates. Static builds (macOS, Linux) have neither a `php.ini-development` nor an `ext/` folder.
**Decision:** (1) **Windows:** start from the zip's own `php.ini-development` and change only the lines lunaRun means to (an `IniEdit` that replaces the first active line of a key, else the first commented one, else appends; uncomments `extension=` lines in place so the file's load order is kept, `exif` after `mbstring`; keeps the file's line endings). A test with the real 8.3.36 file proves that **only the intended lines change**. Extensions are enabled only if their `php_<name>.dll` exists, and the ones that do not are reported. **Static builds:** a small embedded template with no extension lines (their extensions are compiled in). (2) **No template engine:** a few string operations are enough, so `minijinja` is not added (CLAUDE.md "Don't add a dependency to do something a few lines of code can do"). It can still come with the Caddyfile or `my.cnf` if those need loops. (3) **Where files live:** `LUNA_HOME/config/php/<version>/php.ini` and `conf.d/99-user.ini`, plus one `config/php/cacert.pem` shared by all versions. `php.ini` and the CA bundle are **owned by lunaRun and rewritten at every install**; `99-user.ini` is created once and **never overwritten**. Every PHP process lunaRun starts gets `PHPRC=<config>/php/<version>` and `PHP_INI_SCAN_DIR=<config>/php/<version>/conf.d` from `php_environment`. (4) **`extension_dir` is the final install folder**, never the staging folder the files are written in, which is why `InstallCtx` carries `final_dir` and `home`. (5) **CA bundle:** Mozilla's list as published by curl (`cacert.pem`, MPL-2.0, about 200 KB), embedded with `include_str!` from `crates/luna-core/data/cacert.pem`, refreshed by `pnpm ca-bundle`, which refuses anything that does not match curl's published SHA-256 or does not look like a certificate bundle. It is listed in `THIRD-PARTY.md`. (6) **Time zone:** the zone from `/etc/localtime` or `/etc/timezone` on macOS and Linux, validated to plain zone-name characters; `UTC` on Windows, whose zone names differ from IANA's and which Laravel overrides with `APP_TIMEZONE` anyway. (7) **macOS:** after extraction each of `php` and `php-fpm` is checked with `codesign -v` and signed with `codesign --force --sign -` if that fails; `/usr/bin/codesign` is the one system tool lunaRun starts, with an argument list.
**Consequences:** The app carries about 200 KB more and its CA list is as old as the app until the weekly `pnpm ca-bundle` (or a release) updates it; a stale list only matters for a CA added since. Paths that PHP would misread inside an ini string (a quote, a line break or `${`) are refused with `INVALID_PATH`, so a `LUNA_HOME` containing one cannot install PHP. A failed install can leave the version's `config/php/<version>` behind (harmless, overwritten next time, removed on uninstall in task 5). The verify step runs `php -v` without the generated ini, because `extension_dir` points at the final folder that does not exist yet while verifying.

### D-021 — Uninstall: rename first, keep database data, never overlap an install (2026-11-04, accepted)
**Context:** Removing a runtime folder with hundreds of thousands of files takes seconds and can die halfway (a crash, a locked file). A half-deleted folder that still looks installed is worse than either outcome. Users' databases live next to the runtime and are the one thing that must not disappear by accident (FR-RT-06). Services (M1.4) and projects (M1.7) do not exist yet but the checks for them have to be designed now.
**Decision:** (1) After the checks, the install folder is **renamed** to `runtimes/<rt>/.trash-<job>` in one step and only then deleted. From the rename on the version is not listed, and the uninstall always finishes (a rename cannot be undone, so cancel is honoured only before it). If the delete fails (a locked file) the report says `leftover` and the next start removes it (`cleanup_incomplete` handles `.trash-*`). On Windows an open file inside the folder makes the rename itself fail (sharing violation or access denied), which is reported as `RUNTIME_IN_USE` with nothing changed; that was verified with a real exclusively opened file. (2) **Data is kept by default.** An adapter names its data folders per line (`data_dirs`) and they are deleted only with `deleteData` and only if no other installed version of that runtime still names the same folder. Version-specific config goes with the version (`config_dirs`, PHP's `config/php/<ver>`, including the user's `99-user.ini`, which the confirmation must say). (3) "Is a service running" and "which projects are bound" are `UsageChecker` hooks that report nothing until the supervisor and the project store exist; a failing checker stops the uninstall (when we cannot tell whether it is in use, we do not remove it). Bound projects need an explicit `confirmBoundProjects`; running services never can be overridden here. (4) Install and uninstall of one `<runtime>@<version>` share a job key, so they cannot overlap; starting one while the other runs fails with `BUSY` instead of joining the wrong job (`Installer::start` and `Uninstaller::start` return `Result` for that reason).
**Consequences:** Removing a runtime needs free space for nothing (a rename), but deleting it frees the disk only after the second step. A user who uninstalls the last version of a database line and asks to delete data loses those databases for good: the UI must say that plainly. Uninstall does not touch downloads (they are deleted after each install already) or the shared `config/php/cacert.pem`.


### D-022 — The app holds one registry that starts built-in and is replaced in the background (2026-11-04, accepted)
**Context:** The Runtimes page needs a version list the moment it opens, but fetching the hosted list takes a network round trip (or fails offline). The page also has to explain an old list ("you appear to be offline", "update lunaRun") instead of silently showing it.
**Decision:** (1) `luna_core::registry::RegistryHolder` (managed state in `src-tauri`) starts with the list embedded in the app, so the first answer never waits on the network. (2) At startup a background task calls `refresh` (network, then the saved copy, then the embedded copy, see `load.rs`) and swaps the result in as a whole; it then emits `registry:updated` with the new `RegistryStatus`. (3) `RegistryStatus { source: fresh | cache | bundled, ageSeconds, problem, refreshing }` is what the page uses to say where the list came from; a failed fresher source is a `problem`, never an error. (4) A refresh that is already running is not started twice: the second caller gets the current status. (5) The holder, the catalog rows (`Registry::catalog`: support dates, security-only, community build, Rosetta) and today's date (`CalDate::today`, UTC, no new crate) are all in `luna-core`; `src-tauri` only maps commands. (6) `cleanup_incomplete` runs at startup, before anything can install.
**Consequences:** The list can change under the page once, a few seconds after start; the page reloads on the event. A user can press "Check for updates" at any time. If the clock is unusable, `runtimes_available` fails with `INTERNAL` rather than guessing which versions are end of life.

### D-023 — Supervisor: one lifecycle task per service, `Crashed` is final, programs only from `LUNA_HOME` (2026-11-04, accepted)
**Context:** Services (PHP, MySQL, MariaDB, Caddy) must start, become ready, be restarted after a crash, and stop, without two events ever racing (a crash arriving as the user presses Stop) and without lunaRun starting something it should not. SERVICES section 2 had the states and the policy, with one inconsistency: the diagram sent exhausted restarts to `Error`, FR-SV-06 says the service stays `crashed`.
**Decision:** (1) `luna_core::services::Supervisor` runs **one lifecycle task per service**; while it lives it is the only writer of that service's state, and every change goes through a pure table (`ServiceState::next`, every legal and illegal move tested). (2) FR-SV-06 wins: after 3 automatic restarts in 60 s the service stays `Crashed` with `gave_up` (the UI notifies); `Error` means a start that never worked. A failed automatic restart counts as a crash. (3) `ServiceSpec::validate` runs before anything starts: every program, helper, and working directory must be an absolute path that exists and, with `..` and links resolved, is **inside `LUNA_HOME`** (golden rule 6); processes get an argument array and are never started through a shell. (4) The sink is told **before** the new status is visible to waiters, so a caller woken by a state can rely on the event having been delivered. (5) Restart policy, stop plan and timeouts are plain values (`RestartPolicy`, `StopPlan`, `start_timeout`), and the restart policy is a pure tracker that is told the time, so tests use milliseconds or no sleeping at all. (6) Containment (Job Objects, process groups) plugs in through the `Containment` trait; until it exists the only safety net is `kill_on_drop`. (7) Tests use the test program itself as the stand-in service (hard-linked into a data folder with a space and a non-ASCII letter and started with an argument that runs one test), so no real PHP or MySQL is needed on any platform.
**Consequences:** Service output goes nowhere until log capture (M1.4 task 3). A Windows `php-cgi` pool opts into `recycle_on_exit` so its by-design exits are not crashes. The test stand-in measures its "crash after" time from the first connection of the ready check, so the tests do not depend on how fast the machine is.

### D-024 — No orphans: a Job Object or process group per service, PID files, and how the OS is called (2026-11-04, accepted)
**Context:** FR-SV-07: if lunaRun dies, no service may stay running unnoticed, and the next launch must find what is left and offer to adopt or stop it. That needs three things: containment while lunaRun runs, a record that survives a crash, and a way to ask the OS about a process by its number. ARCHITECTURE had planned the `sysinfo` crate for the last and the `windows` crate for Job Objects.
**Decision:** (1) **Containment** is a trait (`Containment`, installed by default as `OsContainment`). Windows: one **Job Object per service** with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, assigned right after the process starts; the OS closes lunaRun's handle when lunaRun dies however it dies and kills everything in the job, and when a service ends normally dropping its job kills what it left. macOS and Linux: one **process group per service** (`process_group(0)`), killed with `kill(-pgid, SIGKILL)` when the service ends; the group does not die with a crashed lunaRun, which is what PID files are for. (2) **PID files** `LUNA_HOME/run/<id>.pid` hold `{pid, exe, startedAt, port}` (schema 1, written atomically through `state`), are written when the process starts and removed **before** the state changes (so whoever sees `Stopped` also sees the file gone). (3) At launch, `Supervisor::scan_leftovers` keeps a file only if the process is **alive and its executable is still the recorded program** (a number is reused; on macOS and Linux "the same program" means the same file on disk, device and inode, because the OS may report another name of a hard-linked file than the one it was started from: macOS did); anything else is stale and deleted, a damaged file too (with the copy `state` sets aside), a file from a newer lunaRun is left alone. `adopt(spec)` tracks a leftover with the normal lifecycle (it must run the spec's program and pass the ready check, else it is left untouched); `stop_leftover(id)` asks it to leave, kills it after ten seconds and kills its group. (4) **Calling the OS:** the `windows-sys` crate (0.61, Windows only, features `Win32_Foundation`, `Win32_System_JobObjects`, `Win32_System_Threading`: it is plain bindings, and `JOBOBJECT_EXTENDED_LIMIT_INFORMATION` is a large struct that is better left to generated code), `/proc` on Linux, `libproc`'s `proc_pidpath` and POSIX `kill` declared by hand on macOS and Linux (a few lines, in the same style as the `kill` declaration already there). **No `sysinfo`:** the few calls needed are shorter than the dependency, and the port-owner lookup of the PortAllocator task needs different calls (`GetExtendedTcpTable`, `lsof`, `/proc/net/tcp`), so it is decided there. (5) A process number that is 0, 1 or does not fit an `i32` is never passed to `kill` (`kill(0, ...)` and `kill(-0, ...)` address lunaRun's own process group). (6) A zombie (ended, not yet collected) does not count as alive on Linux.
**Consequences:** On Windows a hard kill of lunaRun kills every service (an interrupted database does InnoDB crash recovery on its next start, as SERVICES already says). On macOS and Linux a crashed lunaRun leaves its services running and the next launch offers to adopt or stop them. There is a small gap on Windows: a process is in its job a few microseconds after it starts, and `CREATE_SUSPENDED` is not available through the standard library; no service starts children before it has finished starting. `stop_leftover` on Windows is a hard terminate (no polite signal exists for a background process), and the leftover has no spec, so it cannot use a service's own graceful command: adopt it first when a clean shutdown matters. The Unix-only code cannot run on the Windows development machine, so it is type-checked locally for both Unix targets (`CC_<target>=true AR_<target>=true cargo clippy -p luna-core --all-targets --target <target>`, see TRACKER section 7) and run by CI.
