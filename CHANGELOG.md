# Changelog

All notable changes to this project are documented here.
The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and the project follows [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Changed
- New logo: a crescent moon merged with an `R` and an arrow. It replaces the old icon in the app window, the installer, the sidebar, the browser favicon and the README (which switches between a light and a dark version), and a social preview image is included.

### Fixed
- Installing a runtime no longer fails on Windows when the folder name has an accented letter (for example a user profile named José): the check that the new program runs threw away its whole answer when it contained a character the system wrote in its older text encoding.
- Installing or uninstalling a runtime on Windows no longer fails with "Access is denied" when the virus scanner is still looking at the program that was just unpacked: lunaRun now waits up to ten seconds for the folder to be let go before it moves it.

### Added
- Quitting will stop things in a safe order: first the web server, then PHP, then the databases, each group all at once and the next one only when the one before has stopped, so a database is never shut down while a page is still asking it something. A service that does not stop in time is ended and reported (a database that had to be ended will recover by itself the next time it starts), and one that cannot be stopped at all does not hold up the rest. Services that crashed and are waiting to restart are stopped too, so nothing comes back to life in the middle of quitting. Nothing in the app quits this way yet; that comes with the Services page.
- The PHP and web server services are ready: every installed PHP version gets its own pool (on Windows four `php-cgi` workers on consecutive ports that are restarted quietly when they retire themselves; on macOS and Linux one `php-fpm` with a generated config), and Caddy gets a generated Caddyfile for the sites, listens on this computer only, and is checked with `caddy validate` before a running Caddy is told to reload it, so adding a site never restarts the others and a broken file never reaches a running server. Tried for real on Windows with PHP 8.5 and Caddy 2.11 from a project folder with a space and an accented letter: a PHP page served through Caddy, a second site added without a restart, and a clean stop. Nothing in the app starts them yet.
- The database services are ready: MySQL and MariaDB each get a service per version line (for example `mysql@8.4`, `mariadb@12.3`) with a port of their own (3306 when it is free), a config that lunaRun writes and keeps current, and a `user.cnf` of your own that lunaRun never overwrites. The first start sets the data folder up (user `root`, no password, reachable from this computer only) and removes it again if that fails, so it can be retried. Start is confirmed by asking the server, and stop is the server's own clean shutdown. Tried for real on Windows with MariaDB 12.3 and MySQL 9.7 in a folder with a space and an accented letter. Nothing in the app starts a database yet.
- Services now get stable ports and are never started on a port that is taken. lunaRun remembers which port each service uses (sites from 8100, PHP from 9100, databases from 3306, Caddy's admin port 2119), checks the port right before starting a service, and if another program already has it, says which one (for example "XAMPP's mysqld.exe from C:\xampp\mysql\bin") and can pick another port. This also catches programs that listen on all network addresses, which a plain test of the port misses on Windows and macOS. Nothing in the app starts a service yet.
- What a service prints is now kept: each service writes into its own log file (the old files are kept as `.log.1` and `.log.2`, and a running one is trimmed at 5 MB), lunaRun remembers the last 2,000 lines of it and of the log files a service writes itself, and passes new lines on in at most ten batches a second. Because the service writes straight into the file, a service that was running when lunaRun crashed keeps its log and can be taken over again. Nothing in the app shows or starts services yet.
- Services can no longer be left running by accident. On Windows every service now runs inside its own Job Object, so if lunaRun is closed or crashes the system stops them too. On macOS and Linux every service runs in its own process group that is stopped with it, and a small record of each running service is kept, so after a crash lunaRun can find what is still running and offer to take it over or stop it. Nothing in the app starts a service yet.
- Groundwork for running services: lunaRun can now start a program, wait until it answers on its port (or a helper confirms it), watch it, restart it after a crash (up to three times in a minute, after one, two and four seconds, then it stays marked as crashed so you can be told), and stop it politely before forcing it. Programs are only ever started from inside the lunaRun data folder, and a service that never starts is reported as an error instead of being retried. Nothing in the app starts a service yet; that comes with the Services page.
- You can now install and uninstall runtimes from the Runtimes page. Each available version has an Install button; while it runs the row shows the phase, a progress bar with percentage and sizes, and a Cancel button (what was already downloaded is kept, so installing again carries on). Uninstall asks first: the dialog names the version and where its files are, lists the projects that use it, refuses while a service runs from it, and for databases keeps the data unless you tick the box to delete it. Finished jobs are confirmed with a short notice, and problems stay on the page with plain advice: not enough disk space (how much is needed and free), a download that failed its checksum, no internet, and on Windows a missing or too old Visual C++ runtime with the address to download it from, which you can copy.
- The Runtimes page now shows real data: a tab per runtime (PHP, Node.js, Composer, MySQL, MariaDB, Caddy), what is installed on this computer, and the versions available for it, with badges for end of life, security-fixes-only, community builds, release candidates and Rosetta, the download size and the license. It says where the version list came from (up to date, saved earlier, or built into this lunaRun) and why it is not fresher ("you appear to be offline", "update lunaRun"), and has a "Check for updates" button. Installing and removing arrive in the next step. At startup lunaRun also cleans up any install that was interrupted.
- Uninstalling a runtime version: it is moved out of the way in one step and then deleted, so a failure never leaves a half-removed runtime behind. Database data is kept unless you explicitly ask to delete it, and kept while another version of the same line still uses it. lunaRun also refuses to uninstall a version that is running and never installs and uninstalls the same version at once. There is no screen for it yet.
- On Windows, lunaRun now checks for the Microsoft Visual C++ runtime before installing PHP, MySQL or MariaDB, and refuses with a clear message and the download address instead of installing something that cannot start. An outdated runtime (older than version 14.40) is treated the same way.
- Every PHP lunaRun installs now gets its own `php.ini` with Laravel-friendly settings (more memory, bigger uploads, the usual extensions switched on, opcache), a shared bundle of trusted certificate authorities so Composer and other HTTPS calls from PHP work on Windows, and a `conf.d/99-user.ini` for your own settings that lunaRun never overwrites. On macOS the PHP programs are signed so the system lets them start.
- The install flow for runtimes: downloads every part, checks it, unpacks into a hidden work folder, merges the parts (PHP on macOS and Linux is two downloads), checks the new program really runs, and only then moves it into place in one step, so a failed or cancelled install never leaves half a runtime. It also checks free disk space first and cleans up after a crash. There is no screen for it yet.
- Groundwork for installing runtimes: the app now knows what is installed (a receipt per install), what files each runtime provides on each OS, and how to check that an install really runs. The download size shown for PHP on macOS and Linux now counts both parts. Layouts were checked against the real Windows downloads of PHP, Node, Composer, Caddy, MariaDB and MySQL.
- The app now carries the full list of downloadable runtimes inside the installer as its offline fallback (the very file the generator writes), and a daily workflow refreshes that list and proposes the change as a pull request.
- A generator (`pnpm registry`) builds the list of downloadable runtimes from the upstream indexes: PHP (Windows, plus static builds for macOS and Linux), Node.js, Composer, Caddy, MariaDB and MySQL (MySQL downloads are checked against MySQL's signing key; static PHP has no upstream checksum, so its SHA-256 comes from our own download), with checksums copied from upstream (or computed from a download that matched the upstream's own checksum), exact sizes, and end-of-life dates. The first generated list is in `registry/registry.json`.
- The list of downloadable versions is now fetched, saved and falls back safely: a fresh list is validated before it replaces the saved one, the saved copy is used when offline or when the new list is broken or for a newer lunaRun, and a small list built into the app is the last resort. `LUNA_REGISTRY_URL` overrides the address (a local file works for development).
- Registry parser in `luna-core`: reads the list of downloadable runtime versions, ignores fields and downloads it does not understand, refuses a list written for a newer lunaRun, rejects non-HTTPS URLs, bad checksums and unsafe names, orders versions numerically, picks the right download for the computer (with a Rosetta fallback on Apple silicon) and flags versions whose line has reached end of life. New error codes `REGISTRY_INVALID`, `REGISTRY_UNSUPPORTED_SCHEMA`, `NO_ARTIFACT_FOR_PLATFORM`.
- Background job system: long tasks such as installing a runtime get an id, can be deduplicated, report throttled progress through `job:progress` and `job:done` events, and can be cancelled (`jobs_list` and `job_cancel` commands). The Diagnostics page shows a live "Background tasks" list with progress bars and a Cancel button.
- Safe archive extraction in `luna-core` for `.zip`, `.tar.gz` and `.tar.xz`: refuses path traversal, absolute paths, symlink tricks, special files and decompression bombs, keeps the executable bit, supports stripping a wrapper folder, progress and cancellation. New error codes `ARCHIVE_UNSAFE`, `ARCHIVE_CORRUPT`, `ARCHIVE_TOO_LARGE`.

## [0.0.2] - 2026-10-30

### Added
- Project logo and real application icons (replacing the Tauri defaults).
- README with logo, badges and permanent download links for Windows, macOS and Linux.
- "Build & Release" workflow: a manual build button in the Actions tab, and automatic publishing of a tagged release once all three platform builds succeed, with installers renamed to permanent download names.
- CI now runs the Rust tests on Windows and macOS for every push (the repository is public, so runners are free).
- Download engine in `luna-core`: resumable, cancellable, retried HTTPS downloads that are verified against a SHA-256 before the file appears under its final name; redirects to plain HTTP and oversized downloads are refused. New error codes `NETWORK`, `CHECKSUM_MISMATCH`, `CANCELLED`, `INVALID_URL`.

## [0.0.1] - 2026-10-30

### Added
- Dependabot: weekly grouped updates for Rust crates, npm packages and GitHub Actions (Tauri packages grouped; major versions get their own PR).
- GitHub issue forms (bug report, feature request), an issue chooser that routes security reports to `SECURITY.md`, and a pull request template.
- `pnpm bump <version>` sets the version in `package.json`, `tauri.conf.json`, Cargo and `Cargo.lock` and promotes the changelog's Unreleased section, with dry-run, validation and rollback.
- Release workflow: a version tag builds Windows, macOS (universal) and Linux installers into a draft GitHub release; manual runs build one platform as downloadable artifacts. `scripts/check-versions.mjs` refuses a release whose tag and app versions disagree. Windows installer is per-user (no admin).
- Continuous integration (GitHub Actions): lint, tests, generated-types check and a debug app build on Ubuntu; manual Windows/macOS test matrix. Pinned pnpm via `packageManager`.
- First end-to-end command: `app_info` returns version, OS, architecture and data folder to the Diagnostics page, which has loading, error and retry states and a "Copy report" button. Commands are granted individually through generated permissions.
- `luna-core` foundation: typed `LunaError` with stable codes (TypeScript bindings generated), `LunaHome` with guarded `safe_remove`, and atomic, schema-versioned JSON state with corruption recovery and migrations.
- UI design system: light-first theme, Inter font, design tokens, grouped sidebar, dashboard overview, shared Card, PageHeader, EmptyState and StatCard components.
- Project tracker (`TRACKER.md`) for session handoff.
- App shell: sidebar navigation, hash routing, placeholder pages and a light/dark/system theme switcher.
- i18n with typed translation keys and an English strings file.
- ESLint (strict type-checked), Prettier, Vitest + Testing Library, clippy and rustfmt configs, and `pnpm lint`, `typecheck`, `test` scripts.
- Decisions D-011 (React Router, hash mode) and D-012 (ts-rs for generated IPC types); `.cargo/config.toml` export dir.
- Product name and bundle identifier constants in `luna-core`, with a test keeping `tauri.conf.json` in sync.
- Tauri 2 desktop shell with React, strict TypeScript, Vite, Tailwind CSS 4 and shadcn/ui; placeholder window.
- Cargo workspace with the `luna-core` crate and a pinned Rust toolchain.
- Product requirements, architecture, runtime registry, detection, services, build/release and roadmap documentation.
