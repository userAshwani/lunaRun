## 0. The project in five minutes (read this first in a new session)

**What lunaRun is.** A cross-platform (Windows, macOS, Linux) desktop app for PHP and Laravel developers: a modern,
multi-version, **project-aware** alternative to XAMPP, WAMP and Laragon. The owner (GitHub `userAshwani`,
hello@digitallybird.com) works solo; the repo is public, Apache-2.0. The idea: install several versions of PHP, Node,
Composer, MySQL, MariaDB and Caddy **side by side** (downloaded on demand and SHA-256 verified; **no runtime binaries are
shipped in the app or the repo**), run them as supervised services on `127.0.0.1`, and (the headline feature, M1.6) **read a
project's `composer.json`, `package.json` and `.env`, work out which versions it needs, and run it with exactly those**,
offering fixes for what is missing (an extension, a `.env` value). Everything lunaRun owns lives in one folder,
`LUNA_HOME` (on Windows `%LOCALAPPDATA%\lunaRun`): `runtimes/`, `config/`, `data/` (database files), `logs/`, `run/` (PID
files), `cache/`, `downloads/`. It never writes into a user's project folder except through an explicit, previewed action.

**Stack.** Tauri 2 (Rust) shell, React + TypeScript + Tailwind + shadcn/ui front end, pnpm. Rust workspace:
`crates/luna-core` holds **all business logic and never depends on Tauri**; `src-tauri` is a thin adapter (IPC commands in
`commands.rs`, events in `events.rs`, app state in `lib.rs`); the front end is `src/` (`features/<area>`, shared
`components/`, generated Rust types in `src/bindings/` by ts-rs, English strings in `src/i18n/locales/en.ts`). Docs:
[PRD](docs/PRD.md) (what and why, requirement ids `FR-...`), [ARCHITECTURE](docs/ARCHITECTURE.md) (layout, IPC),
[ROADMAP](docs/ROADMAP.md) (the checklist), [DECISIONS](docs/DECISIONS.md) (D-001 to D-031), and the topic docs
[RUNTIMES](docs/RUNTIMES.md), [SERVICES](docs/SERVICES.md), [PROJECT-DETECTION](docs/PROJECT-DETECTION.md),
[BUILD-AND-RELEASE](docs/BUILD-AND-RELEASE.md).

**How things are verified (keep this pattern).**
1. Pure unit tests and exact golden strings (generated config text is compared character by character).
2. A **stand-in service**: the test binary itself, hard-linked into a folder with a space and a non-ASCII letter, behaving as
   environment variables say (`crates/luna-core/tests/stub_service/mod.rs`). Supervisor behaviour is tested with it.
3. Opt-in **real** tests (`#[ignore]`): `runtimes_online`, `databases_online`, `web_online` install the real MariaDB, MySQL,
   PHP and Caddy through the real installer, run them through the supervisor and talk to them. They ran and passed on
   Windows; they have **never run on macOS or Linux** and are not in CI (they download 100 to 330 MB).
4. **Mutation checks**: a script breaks each important behaviour on purpose (backs the file up, replaces one piece of text,
   runs the tests, restores the file) and every mutation must be caught by a test. Recreate such a script in the scratchpad
   per task.
5. `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`, and clippy for the Linux and Intel macOS
   targets (the Unix-only code cannot run on this Windows machine; recipe in section 7).
6. CI on Windows, macOS and Linux for every push; the Unix-only code is proven only there. Anything that touches IPC or the
   UI must also be checked in the real app window (recipe in section 7).

**Traps this project already hit (do not relearn them):**
1. **Windows text encodings.** Programs print paths in the ANSI code page: never `read_to_string` a program's output or log
   (read bytes, decode lossily). **MySQL reads `my.ini` in the ANSI code page**; MariaDB, PHP and Caddy read UTF-8 (D-027).
2. **Antivirus holds fresh programs.** Moving a just-run runtime folder can fail with "Access is denied": use `rename_dir`
   (a short retry).
3. **macOS names any hard link of a program.** Identify a program by file identity (`same_program`), never by name (D-024).
4. **A bind to `127.0.0.1` succeeds while another program listens on the wildcard address** (Windows, macOS, XAMPP's
   `mysqld`). "Taken" means the bind fails **or** the OS lists a clashing listener (`check_ports`, D-026).
5. **Never keep a test-bind listener alive while asking the OS who listens**: every port then looks held by yourself. It
   happened in `check_ports` (now a regression test) and made suites hang.
6. **Test ports** come from a counter in 20,000 to 29,999 and are chosen with `check_ports`; never ask the OS for a port and
   probe it by binding (the probe is a real listener for a moment).
7. `.gitignore` hides `*.pem` (an embedded `cacert.pem` needs an explicit exception) and `.gitattributes` normalises line
   endings (a fixture whose bytes matter needs a `-text` rule).
8. Tauri mock-runtime tests must be integration tests in `src-tauri/tests/` (Windows manifest).
9. A new IPC command needs the function, `COMMANDS` in `build.rs`, `generate_handler!`, a capability entry and a typed
   wrapper: forgetting the capability fails only at runtime (check in the real window).
10. CHANGELOG entries go under `## [Unreleased]` only, never under a released version.
11. **A probe socket and a process being created must not overlap** (Linux and macOS fork): the child inherits the probe and the port looks listened to by nobody. Probes and spawns in `services` take the lock in `services::gate` (D-030).

**Practical notes for sessions on this machine.** Foreground commands are limited to 10 minutes: run `cargo test --workspace`
in the background writing to a file in the scratchpad and read the file afterwards. A shell heredoc that contains quotes can
break: write a small Python script with the Write tool and run it with `python -I`. Do not judge whether a test binary is
stale from its `.exe` time: let cargo decide (`cargo test -p luna-core --test <name>`). Never leave a mutation script's
backup file behind (`find . -name "*.mutbak"`). The owner's XAMPP (`d:\xampp`) runs on this PC and holds port 3306: never
touch it (the real tests therefore get 3307).

## 5. Known issues and caveats

- **First `pnpm tauri build` is slow** (about 8 min cold, about 4 min incremental, LTO). For UI work use `pnpm dev` + a headless browser instead.
- **Windows signing:** none yet. Installers will trigger SmartScreen until signed.
- **The repository is public** (since 2026-10-30): standard runners are free, release downloads are public, history is public (commit author email `codeashwani@gmail.com`, owner's choice). D-015 supersedes the private-repo cost control D-013, so CI runs the Windows and macOS tests on every push. Branch protection/rulesets are now available for free (Settings > Rules), not set up. Enabling *private vulnerability reporting* (Settings > Code security) is recommended because SECURITY.md points to it. Both are owner actions.
- **Resolved:** the artifact-quota failure was specific to the private repo. Since the repo became public, manual builds upload artifacts normally (verified: 7 artifacts).
- **Release pipeline verified end to end, twice:** `v0.0.1` (draft path, tag push, three platforms) and `v0.0.2` (fully automatic: tag push, builds, `publish` job renames the assets and publishes). Still unproven: that the installers *install and launch* on a real Windows or macOS machine (owner smoke test), signing and notarisation (none yet: Windows SmartScreen warning, macOS Gatekeeper needs right-click > Open), and the auto-update path (Phase 2). The Windows `-setup.exe` is a 32-bit NSIS stub by design (PE machine `0x14c`), which installs the 64-bit app. To release again: write notes under `## [Unreleased]`, `pnpm bump X.Y.Z`, commit, push, wait for CI, `git tag -a vX.Y.Z -m "lunaRun vX.Y.Z" && git push origin vX.Y.Z`; the workflow does the rest. The tag creation is the step to confirm with the owner.
- **Installer sizes (measured at `v0.0.1`):** Windows 1.6 MB (NSIS) / 2.3 MB (MSI), macOS 4.2 MB (dmg), Linux `.deb` 2 MB, but the Linux **AppImage is 77 MB** because it bundles WebKitGTK. PRD NFR-01 (20 MB) therefore applies to Windows and macOS only, and the PRD says so. Sizes will grow once real features land: re-measure at `v0.1.0`.
- GitHub warns that `ubuntu-latest` migrates to Ubuntu 26 from 2026-10-19. CI uses `ubuntu-latest` and passed. Release builds pin `ubuntu-22.04` on purpose (older glibc, wider compatibility). If CI breaks on Linux for no code reason, check the runner image.
- **Issue forms render is unconfirmed:** the two forms pass schemastore's official schema and GitHub parsed `config.yml` (its API returns the security contact link), but GitHub's APIs (`community/profile`, GraphQL `issueTemplates`) only report Markdown templates, so they show no issue template even though forms exist. **Owner check, 10 seconds:** open https://github.com/userAshwani/lunaRun/issues/new/choose and confirm "Bug report" and "Feature request" appear (and no blank-issue link). If not, the form YAML needs a fix.
- **HTTPS path is verified only by an opt-in test:** `cargo test -p luna-core --test download_online -- --ignored` (needs internet, hits apache.org, pinned SHA-256). It passed on Windows once. Run it after touching `download.rs`, TLS features or the HTTP client; CI does not run it (it must not depend on the internet). The loopback tests cover everything else with plain HTTP. Not tested at all: corporate proxies and TLS-inspecting firewalls (the app uses system proxy settings and the OS trust store, D-014), and macOS/Linux behaviour of the TLS verifier.
- **Extraction: Unix-only tests ran on Linux and macOS CI.** First CI run: every Unix-only security test passed (symlink escapes, write-through-a-symlink attacks, hard links, permission bits) and exactly one test failed on both: the reference `official.zip` fixture had been created by Python on Windows, which stores the entries as MS-DOS (create_system 0) without Unix mode bits, so the executable bit could not survive. The fixture was regenerated with `create_system = 3`. Lesson: reference archives must be generated as Unix-made to carry modes (a real Windows-made zip carries none, which is fine because Windows runtimes are only extracted on Windows). The Unix-only guards were then mutation-checked on CI (see the done log): every broken guard is caught on Linux and macOS.
- **XZ speed is unmeasured in release:** the pure-Rust decoder took 31.6 s for Node's 32 MB (201 MB unpacked) `.tar.xz` in a *debug* test build, and the Windows zip of Node took 13.7 s in debug. Release is normally several times faster. Measure with `cargo test --release -p luna-core --test extract_online -- --ignored --nocapture` before M1.3 shows an install progress bar. Extraction progress for tar archives has no total (`bytes_total` is `None`), so the UI should show an indeterminate bar for those. If too slow, see D-016 (liblzma or the multi-threaded reader).
- **Extraction is not atomic:** on error the destination may hold part of an archive, so callers extract into a fresh `runtimes/<rt>/.staging-<uuid>` folder and remove it with `LunaHome::safe_remove` (the job pipeline test shows exactly that pattern). Windows refuses symlinks inside archives on purpose (Windows runtimes are zips).
- **Live job events are proven end to end** (M1.3 task 6b): in the real window a real MariaDB install showed moving progress and Cancel stopped it, and a real Caddy install and uninstall ran with their toasts. Jobs live in memory only (they do not survive a restart, which is intended: installed runtimes persist, jobs do not), so a failed attempt shown on the Runtimes page is gone after a restart.

## 9. Setting up a new computer (autonomous bootstrap)

**When:** the owner has unzipped or cloned the project on another PC and sends "start work" (often with only this file
attached), or `node scripts/check-machine.mjs` prints `NOT READY`. Do all of it **yourself, in order, without asking**: every
step first checks and installs only what is missing, so it is safe to repeat. The few things only the owner can do are in 9.5.
Nothing here replaces the normal workflow: when the machine is ready, continue with the *Next step* in section 1.

### 9.1 What the owner brings

The whole project folder as a zip, this file included. **Exclude `target/` and `node_modules/`** (many gigabytes, rebuilt
automatically, and not portable between operating systems) and **keep `.git`**. Nothing secret is in the folder: the GitHub
login is **not** copied, so the new PC needs its own (9.4). What was said in earlier chats does not travel either: this file is
the memory, which is why it is long.

### 9.2 The steps

0. **Orient.** Open a terminal in the folder. `node -v`: if Node is missing, install it first (9.3), because the check script
   needs it. `git rev-parse --is-inside-work-tree`: if that fails, the zip had no `.git` or the owner gave you only the GitHub link; run
   `git clone https://github.com/userAshwani/lunaRun.git` beside it (public, no login needed) and work **in the clone** from
   here on.
1. **Check.** `node scripts/check-machine.mjs` (or `pnpm check:machine`). It prints one line per check and, for anything not
   ok, the command that fixes it on this operating system. Install every `MISSING` item (9.3), in the order printed, and run
   it again until it says `READY`. Warnings are advisory (`behind origin/main`: `git pull --ff-only`; a different pnpm:
   fix it; `gh` not logged in: 9.4). A tool that was just installed is usually **not on the PATH of the terminal that
   installed it**: open a new terminal, or on Windows make sure `%USERPROFILE%\.cargo\bin` and `%APPDATA%\npm` are on it.
   The first `rustc` inside the repo makes rustup fetch the toolchain `rust-toolchain.toml` pins (1.99, with rustfmt and
   clippy): that takes a minute.
2. **Update.** `git pull --ff-only`. If it cannot fast-forward because of local changes, **stop and tell the owner**; discard
   nothing.
3. **Dependencies.** `pnpm install --frozen-lockfile`. (Rust crates are fetched by the first build.)
4. **Prove the machine** with the smoke gate, long commands in the background writing to a file (the first Rust build compiles
   about 500 crates and takes several minutes): `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets -- -D
   warnings`, `cargo test --workspace`, `pnpm typecheck`, `pnpm lint`, `pnpm test`. All must pass. A failure that exists
   **only on this machine** is a finding: diagnose it, fix the code if the code is wrong, and note it in the done log.
5. **macOS or Linux only: the unverified-Unix debt.** The code for these systems has only ever been type-checked and run by CI;
   the opt-in real tests have **never run on a Mac or Linux box**. Right after the smoke gate, before the *Next step*, run the
   three of them, each in the background with its output in a file (100 to 330 MB of downloads, 2 to 6 minutes each):
   `cargo test -p luna-core --test databases_online -- --ignored --nocapture`, the same for `web_online` and for `runtimes_online`.
   Whatever they show is a real bug in shipped code (the likely places: MariaDB's Unix setup arguments and the Unix socket
   in `services/databases.rs`, `php-fpm` and its `php-fpm.conf` in `services/php.rs`, the Unix branches of `check-machine`
   itself). Fix it, and record the results in section 5 ("Database facts (3)" and "Web service facts (3)") and the done log.
6. **Write the machine down.** Add a block "6b. This machine (<system and version>, <date>)" to section 6: the system, the
   tool versions the check printed, anything unusual. Leave the first machine's notes alone.
7. **Commit and continue.** Commit anything this changed (the tracker, a fix) with a Conventional Commit and **no AI
   attribution**, push, then do the *Next step* of section 1 as usual and stop after it, as always. If nothing tracked
   changed, there is nothing to commit.
